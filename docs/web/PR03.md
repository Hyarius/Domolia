# PR03 — Sauvegarde/restauration Android ↔ Web

## Périmètre

- Implémenter le contrat `docs/web/backup-format.md` et son codec versionné + validation stricte.
- Ajouter une API de lecture cohérente de tous les Livres, Parties, métadonnées non sensibles de profils, bindings et préférences exportables ; la couverture est incluse par ses octets.
- Afficher `Paramètres → Données et sauvegardes` sur Android **et** Web avec `Sauvegarder mes données` et `Charger mes données`, nombre d'éléments et exclusions de secrets.
- Télécharger/partager le fichier sur chaque plateforme sans aucune transmission automatique.
- Avant import, afficher résumé et choix Fusionner / Remplacer ; planifier collisions puis restaurer avec transaction SQLite et stratégie de reprise pour stores annexes.
- Conserver et signaler séparément les connexions IA sans secrets ; autoriser leur reconfiguration.
- Préserver `BookSession.aiProfileId` si la PR #7 est fusionnée, l'ordre réel des Parties et les journaux/diagnostics non exportés.

## Tests et acceptation

- Corpus commun Android ↔ Web, restauration sur autre navigateur, nouvelle machine simulée, base vide, collisions multiples et fusion idempotente.
- Aucune disparition des données initiales en présence d'un fichier tronqué, d'une erreur de validation, d'un quota dépassé ou d'un crash simulé.
- Images réelles conformes, conversations et scènes intactes ; archives sans clé API ni jeton ni diagnostic brut.
- Prendre en compte taille/temps de traitement des gros historiques ; UI non figée.
- `flutter analyze` / `flutter test` et validation Android/Web obligatoires. Pas de report optionnel de cette PR.

## Mise en œuvre sur `impl/web/03-portable-backup`

- Branche issue de `d9a6a890`, dernier commit de PR02 à l'ouverture ; PR empilée #10 (base `impl/web/02-indexeddb-bootstrap`).
- `lib/backup/portable_backup.dart` : JSON v1 strict, limites de taille, relations, couverture, chronologie, metadata non secrète. Refus des URL de profil avec paramètres, identifiants intégrés ou fragments, et des champs d'événement inconnus.
- `lib/backup/backup_repository.dart` : capture cohérente via transaction de lecture ; restauration Livres/Parties/liaisons via une seule transaction SQLite, conflits déterministes, import idempotent et prise en charge de `sessions.profile_id` si la migration v3 est disponible.
- `lib/backup/backup_service.dart` : import des métadonnées IA **sans clés**, IDs remappés pour ne pas associer les données à un token local ; écriture additive avant transaction SQLite, compensation en cas d'échec SQL.
- `lib/backup/backup_settings_page.dart` : boutons sauvegarder/charger sur Android et Web, aperçu, fusion/remplacement avec confirmation forte ; l'app attend les écritures de conversation avant import et refuse d'importer pendant une génération IA.
- Tests du codec et des erreurs, appareils simulés avec deux bases SQLite, collision/idempotence, remplacement, rollback et sécurité des tokens ; test Chrome/IndexedDB exécuté par `.github/workflows/web-check.yml`.

### Limitations et validations restantes

- GitHub Pages de préversion ne peut toujours pas être publié sans activation manuelle de Pages dans les paramètres du dépôt. Ce blocage ne concerne pas la compilation/test Web.
- Valider **manuellement** les boîtes de dialogue d'import/export `file_picker` sur Android, Chrome, Firefox et Edge ; tester arrêt/redémarrage du navigateur et des tailles de sauvegarde importantes.
- PR #7 restant non fusionnée : schéma SQLite v2 actuel, sessions sans `profile_id`. Les archives possédant une liaison IA propre à la Partie sont explicitement refusées tant que v3 n'est pas disponible, plutôt que de perdre la liaison.
- Les préférences exportables v1 sont actuellement une liste blanche **vide** ; aucun réglage externe n'est importé silencieusement.
- Les métadonnées IA sont stockées hors SQLite. La compensation est vérifiée lors d'une erreur SQL ; un arrêt brutal entre l'ajout (sans secret) de ces profils et le commit peut laisser des profils non liés à nettoyer plus tard, mais ne supprime pas les Livres préexistants. Un véritable journal de reprise multi-store reste à développer pour une atomicité de bout en bout.
